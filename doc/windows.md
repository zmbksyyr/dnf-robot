# Windows 宿主

Robot 保持独立项目。Linux 使用原有 `/proc`、信号及启动脚本；Windows 使用同一业务代码和本项目的平台实现。宿主差异由配置目录内 `conf/host-profile.json` 描述，不依赖外部 GUI 的进程名称或界面控件。

## 接口和生命周期

`--config-dir` 指定 Robot 自己的配置、模板、PVF 导出、密钥、状态和日志目录。Windows 可选 `--stop-event`、`--ready-event` 分别接收正常停止请求、发出首次初始化完成通知。外部控制器只需要准备 game 目录中的配对密钥并提供宿主 profile；Robot 自行同步密钥和初始化业务文件。

profile 为 version 1，包含服务的 executable、image、image_sha256、pid_file、directory、start 参数及 stop_event。Windows 在接受 PID 前核对进程路径、原 ELF 文件 SHA-256 和已映射 ELF 头；不把同名进程当作目标。game、auction、point 为运行契约必需项，monitor、relay 可提供用于诊断中的身份关联。未知目标或旧字节不同明确失败。

Web 的重启操作在 Windows 同一 PID 内关闭并重建 Robot 的运行资源，保留外部控制器的进程和停止事件归属；仅首次启动使用 ready 事件。Linux 保留原有进程重启路径。停止会先取消新的后台工作与未完成登录确认，再等待已经开始的操作退出；错误关闭返回非零状态。

HTTP 子进程关闭监听后，还会等待 `http.Server.Shutdown` 排空活动响应，再返回并退出。此前只等待 `ListenAndServe` 返回，带 42 个摊位热重开时曾使 HTTP 重启请求收到连接重置，尽管 Robot 主 PID 已成功重建。这是公共 HTTP 生命周期修复，Linux 同样等待已有请求结束，不改变 Linux 的重启入口、脚本或业务协议。真实 HTTP 回归在移除该等待时失败，恢复后连续 10 次通过；全仓测试、Web race 及 Linux amd64 交叉编译通过，记录为 Native 仓库外 `robot-http-regression.json`、`robot-http-full.log`、`robot-http-race.log`。

关闭也会中断同账号重登、选角存档、离线清理和分解摊确认等待。离线清理返回取消错误，不能作为数据库写入的安全许可；正常运行和仅停止自动行为时仍保持原有存档边界。这些取消及批量操作改进属于公共修复，Linux 同样使用。

所有 actor 的正常退出共用 16 个并发名额，覆盖停止自动行为、缩容和进程关闭，
对支持返回选角、当前运行且未组队的角色，先沿用 CMD 7 保存并卸载角色，收到原
服务确认后才关闭连接；进程关闭期间仍可完成这个保存，但不授予数据库写入许可。
保存拒绝或超时明确失败，进入既有强制关闭路径。随后执行原有 500 ms 本地关闭
确认，再查询服务端账号状态：每 100 ms 检查一次，

不确认退出成功，也不清理缓存。这只控制退出负载，不替代既有存档稳定期和写库屏障。

## 平台行为

| 功能 | Windows 行为 |
| --- | --- |
| 创建、上下线、移动、喊话、普通摊和分解摊 | 共用业务和协议实现；手动批量上线沿用登录速率，所有 actor 正常登出共用 16 个并发名额 |
| 分解摊 | 等待完整登录后，单独启动 20 秒机器确认窗口，避免登录过程提前耗尽确认预算 |
| 市场服务及 iteminfo | 从 profile 启停原服务；重建与同步使用现有备份、冲突检查和恢复逻辑 |
| 市场内存补丁 | 根据宿主内存模型核验地址、旧值、写入和回读；Windows refine-banks-31 保留均价上限 7，搜索上限 31，等级上限 127 |
| 组队和邮箱补丁 | 对已验证 game 的线程暂停、核对并修改内存、回读及恢复线程；不安装驱动或系统服务 |
| 运行脚本 | `/root/run`、`/root/stop` 在页面置灰，API 同样明确拒绝；由宿主控制器启停 |
| 在线上限 | 读取实际 game 配置，允许 1–600；修改后提示重启 game |
| 资源与诊断 | Windows API 统计实际 CPU 时间和工作集；netstat 与 tasklist 结合 profile 显示真实服务身份 |

Windows 的 CPU 百分比与 Linux 相同，以单核算力为 100%；工作集和 Linux RSS 不等于 Go 堆大小。socket 使用可复用的 32 KiB 读缓冲，断开时释放库存、摊位、组队和城镇缓存，保留重连所需令牌及密钥。

普通摊、分解摊的准备和到期收摊共用已有并发名额。名额不足时保持现有摊位，下一轮重试到期清理；清理后的恢复必须等角色实际进城才释放名额。此前收摊不受限制、会话确认早于进城，使准备和清理叠加，600 目标下曾出现 546 运行、51 连接中。这是公共调度修复，Linux 同样适用，未改变保存完成后才允许写库的边界。

拍卖搜索保护 v7 使用已有孔记录覆盖包数据，取消可能对缺失 PVF 物品解引用的 `CDataManager/CItem` 调用；保留无记录时的原包、重入保护及异常记录。Windows 首次初始化会更新已识别脚本段并备份，Linux 保留原有显式安装方式。未知自定义 hook 拒绝自动改写。

## Linux 实际对照（2026-11-18）

在同一台 Windows 10 x64 19044.1288 测试机上，先后运行 WSL2 5.10.16.3/Ubuntu 22.04.5 中的原版 ELF 与 Native Windows 宿主；Windows 开始前已正常停服并终止 Linux 测试发行版。两端使用相同 stock PVF、MySQL 5.7.44 冷库、600 个新建 50–70 级角色及 DP2/Frida。Go 1.26.4 amd64、CGO 关闭；构建收据的 513 项源码和内嵌资源哈希与 `1a17552` 一致。它是同机 Linux 内核对照，不是裸机 Linux 结论，也没有把 WSL 引入 Windows 产品依赖。

Linux 先实际创建 600 个角色，再以同一冷库验证两端登录、移动、600 在线持续 60 秒、批量登出、连续 300 秒 550+ 混合行为，以及 Web 重启后连续 120 秒 550+ 恢复。首段有效混合样本 Linux 590–600，Windows 589–600；两类摊位均有成功记录，也保留失败计数。Linux 首次角色创建与六项市场内存补丁实际回读通过，组队/邮箱状态已实际读取；Windows 角色创建、各补丁及客户端业务的原有证据仍单列。

## 进副本请求被前置状态卡住（2026-11-21）

给 `parsePacket` 临时加收包跟踪（已回滚）后取得确凿序列：登录后 `typ=2`；发
`SetPartyInfo`（类型 12）后服务端回 `typ=9 size=47` 的队伍信息——说明**建队成功**；
随后发 `SelectDungeon`（16）与 `StartGame`（15），服务端只回 `23/3/2/26/27` 等常规包，
始终没有 `DisPatcher_SelectDungeon::process` 记录，会话仍停在城镇。

对照只读参考的 `check_error`（`DisPatcherCore/check_error_9.inc`）：
`user->get_state()` 必须为 **5 或 0xd**，否则直接返回 0x7fffffff（静默丢弃，
process 与 trace 都不会执行）。因此问题不在包体、副本号或队伍（队伍已建成），
而在服务端的用户状态未进入“可进副本”的那一档。已试过：补发 `FinishLoad`（40）、
`m_field10=2` 的免队伍分支、副本号 1 与 10000，均无变化。

下一步应找出使 `CUser::get_state()` 变为 5 的客户端包序列（真实客户端进图前必然发过），
再补进夹具；这比继续试副本参数更接近根因。

## 协议级队长成功进图（2026-11-21）

`ReqPeer`：`short peerIdx` + `byte requestType(0=组队)` + `int cookie`；客户端从城镇实体
记录里取对方的 unique id。夹具据此实现：登录并 `FinishLoad` 后读取本会话已记录的
`townEntityPositions`，对其中每个 id 发送一次组队请求，收到队伍快照即停止。

实测：把机器人 17000020 用 API 往复移动后，实体表从 1 个（只有自己）增加到 3 个
（`54393/37414/50894`），三次邀请都发出、服务端也回了 `typ=10 size=23` 的应答，
但机器人侧没有任何 `PEER_REQUEST` 日志，本会话 `partySelfPeer.uniqueID` 仍为 0，
即**队伍未成立**。已排除：请求体长度（16 字节填充）、发送时机（进房/移动中）、
目标数量（逐个尝试）。未确认：`peerIdx` 是否应为服务端世界索引而不是实体引用里的
unique id，以及该应答包里是否携带拒绝码（应答体加密，未解码）。

结论：进副本的队长路径已通，**队长与机器人同队**仍是缺口；没有队伍时机器人不会跟随，
因此副本闭环的最后一段仍无实机证据。夹具保留在 `live` 构建标签内，不进入正式包。

## 邀请失败的根因：城镇实体解析与本客户端不符（2026-11-21）

把机器人用 API 往复移动、让它在同镇广播实体后，队长的 `townEntityPositions` 确实增加了
条目（最多 6 个），但打印出来的坐标是 `(5511,57549)`、`(60394,21794)` 这类明显越界的值，
而机器人当时的真实坐标是 `(647,252)` 一带。这说明当前客户端发出的城镇实体包（类型 22/23）
与仓库里已有的解析器不一致，记录下来的 unique id 也是错的——邀请自然打到无效目标，
服务端回一次 `typ=10` 应答后就没有下文，机器人侧始终没有 `PEER_REQUEST`。

由此可以确定：邀请链路本身（包类型、请求体、时序）没有问题，**缺的是这一版本城镇实体包的
正确解析**。修正解析后，队长的邀请目标才会是真正的玩家，机器人也才会收到组队请求并自动接受。

另外确认了界面侧的事实：客户端在城镇可用鼠标打开 `Town Map`（右上角卷轴按钮），地图上能看到
`洛兰` 等副本入口；键盘（含 SendInput/扫描码）仍只影响朝向，不能移动，也不能触发快捷键。

## 城镇实体包的诱饵候选（2026-11-21）

临时跟踪确认：每个 22/23 实体包会给出**两个候选体**，真实的一条形如
`25 01 04 03 0a 01 05 d0 00 …`（unique 293、坐标 (772,266) 一类合理值），
另一条是同长度的诱饵 `13 24 8b ac …`，按同一布局解析会得到 (44171,35620) 这类越界坐标。
旧选择器在两者都能解析时按来源优先级挑选，可能选中诱饵，于是记录下错误的 unique id 与坐标
——这正是上一轮"邀请打不到真机器人"的直接原因。

修改：`parseTownEntityPosition` 与 `parseTownEntityArea` 增加坐标可信范围
（`maxTownCoordinate = 4000`），越界候选直接判为无效；选择器随后只会拿到真实记录。
新增 `party_state_town_entity_test.go` 用真实/诱饵字节对照。修复后同镇实体表变为
`self 322/(1000,300)` 与 `robot 293/(1498,335)`，并据此成功邀请到机器人：
探测端 `party formed: self=323 peers=4`、机器人日志 `[PARTY_AUTO_ACCEPT] ... peer_unique_id=324`
与 `[PARTY_SELF_ID_RECOVERED] slot=1 unique=293`，`party=true`。

这同时是产品侧城镇跟随的解析修复：此前遇到诱饵候选会记录错误的队友坐标。

## 队长与机器人同时进入副本（2026-11-21）

把顺序固定为「机器人重登（回到城镇 area 0）→ 队长在等实体时开始推动机器人 → 实体表出现两个 id
→ 邀请 → StartGame(15) → SelectDungeon(16) → FinishLoad(40)」后，流程可以稳定复现：

- 02:18:56 机器人 `[PARTY_AUTO_ACCEPT] uid=17000020 peer_unique_id=334`（队长会话）；
- 02:19:06 机器人 `[PARTY_DUNGEON_SKILL_PROFILE] ... auto=true`，即它已在副本房间并加载技能档案；
- 队长侧 `party=true`、`dungeon=yes`，随后驱动自身走了 16 步（x 1000→1480）。

这验证了闭环的前两段（进副本、进房间）在真机上是通的。但机器人侧 `learned_candidates=0`：
职业 9 只有 1 条目录条目且未被学到的技能匹配，因此它不会施法（该职业也不在已核实的普攻职业里）。

仍未打通的是“跟随与击杀”：机器人追随的是**队伍 UDP 通道**里的队长动作帧，而夹具队长只发了
TCP 的 SetPos，没有发队伍 UDP 帧，所以机器人拿不到队长位置（房间 `actors=0`），也就不会移动或攻击。
下一步是让夹具按队伍传输格式（`buildPartyDungeonMotion`/`buildPartyUnreliablePacketChecked`）
向机器人的队伍端口发送队长动作，复用现有构造器即可。

## 队长动作进入机器人跟随循环（2026-11-21）

夹具补上两件事后，机器人的跟随分支被真正驱动起来：

1. **按队伍传输发送队长动作**：用 `buildPartyDungeonMotion` +
   `buildPartyUnreliablePacketChecked` 组装队长动作帧，经 `sendPartyTransportUnsafe`
   发到机器人的队伍端口（不是 TCP 的 SetPos）。实测机器人连续记录
   `[PARTY_DUNGEON_FOLLOW] uid=17000020 peer=17000015 slot=0 route=1 reliable=false queued=1 delay=369ms`。
2. **帧里带上机器人自己的实体**：真实客户端的一帧会描述它看到的全部实体，机器人正是从
   这样的帧里得知自己的坐标。只发队长一个实体时，机器人 `actors[self].position` 未知，
   导航分支直接返回；补上第二个实体后才有可用的自身位置。

当前状态：队长与机器人在同一副本房间（`party=true`、`dungeon=yes`），机器人在副本内加载技能档案
并持续消费队长动作。仍未验证的是“机器人是否真的移动/攻击”：验证器所在进程看不到机器人进程内的
副本坐标，日志也只记录入队不记录位移，因此本轮不宣称跟随位移与击杀通过。要闭环还需要一个可观测点
（例如让夹具统计收到的机器人队伍帧数量，或让机器人在副本内上报自身坐标）。

## 副本内导航的可观测性（2026-11-21）

为了回答“机器人到底有没有在副本里动”，在 `navigatePartyDungeonUnsafe` 增加两条限流（5 秒）
诊断：`[PARTY_DUNGEON_NAV]` 打印自身/队长的坐标已知位、双方坐标与 `active/move`，
`[PARTY_DUNGEON_MOVE]` 在真正发出移动帧后打印 `from/to`。实机日志：

```
[PARTY_DUNGEON_NAV] uid=17000020 self=(7) leader=(7) from=(1450,300) to=(1500,300) active=true move=false
```

由此定位到一个此前看不清的事实：导航的开关是**房间里有活着的怪**。没有怪物时
`planNavigation` 的 `navigation.active` 恒为 false（设计如此：进房先用队长动作回放，观察过战斗后才
独立导航），所以单人预演的房间永远 `active=false`。夹具随后在队长帧里带上怪物实体，机器人立即
`active=true`，说明“看到怪 → 进入接近分支”这条链路是通的。

同时确认了一处设计边界（本轮的改动尝试因此回滚）：把“无怪也直接跟队长”的改动加进去会破坏
`TestNavigationFollowsAfterDeathAndResetsAtRoomBoundary` 的既有约束——进房后用队长回放、
观察过战斗再独立导航，是有意为之，不是缺陷。

`PARTY_DUNGEON_MOVE` 目前尚未出现：`move` 在观测点恒为 false（多数调用落在 200ms 限流窗口内），
因此**机器人真实位移仍未取得证据**，本轮不宣称跟随位移通过。

## 机器人在副本里真的走了（2026-11-21）

上一轮 `move` 恒为 false，加上原因码后立刻看清是 `reason=tick-wait`：导航间隔 200ms 与
队伍帧到达节奏 200ms 相同，浮点相位让几乎每次调用都“早了零点几毫秒”，机器人因此**永远轮不到移动**。
这不是夹具造成的巧合——任何以接近 200ms 节奏驱动该函数的场景都会同样饿死。

修复：给间隔判断加 20ms 容差（`partyDungeonNavigationSlack`），一个整间隔之后的调用必定放行，
更快的调用仍被限流。实机日志随即出现真实位移：

```
[PARTY_DUNGEON_NAV]  uid=17000020 ... from=(1430,300) to=(1480,300) active=true move=true reason=move
[PARTY_DUNGEON_MOVE] uid=17000020 peer=17000015 from=(970,300) to=(1010,300)
[PARTY_DUNGEON_MOVE] uid=17000020 peer=17000015 from=(1450,300) to=(1490,300)
[PARTY_DUNGEON_NAV]  uid=17000020 ... active=true move=false reason=in-range
```

即机器人朝目标分步前进（每步 ≤40）、进入攻击距离后停住（`in-range`），并且确实把移动帧发给了队长。
至此“进副本 → 与队长同房间 → 看到怪 → 接近”在实机上全部打通。

仍未打通：**攻击**（该角色职业 9 无已学技能，`learned_candidates=0`）、清图判定、过图与回城。
`[PARTY_DUNGEON_MOVE]` 与 `[PARTY_DUNGEON_NAV]` 使用各自独立的 5 秒窗口，否则同一调用里后者会吞掉前者。

## 攻击分支的前提条件（2026-11-21）

追查“为什么到了攻击距离却不打”，代码给出了明确答案：普通攻击
（`tryPartyBasicAttackUnsafe`）有硬性前置——

```
partySkillJob == 0 || partySkillJob == 8        // 只有这两个职业走旧式技能通道
&& partyDungeonLegacySkills                      // 队长也在用旧式通道
&& partySkillLoaded
```

在线机器人 17000020 是职业 9，目录里该职业只有 1 条（skill_index 235），而角色没学它
（`learned_candidates=0`），于是既无技能可发、也不满足普攻职业——**攻击分支根本不会进入**。
这不是缺陷，是当前实现的有意边界。

想换一个职业 0/8 的机器人，实测被登录校验挡住：`17000019` 登录返回
`login_rejected ... disconnect_reason=36`（背包校验），与本轮之前记录的夹具角色问题一致；
职业 8 的账号分布在斯顿雪域/西海岸/公会大厅，与队长所在的艾尔文防线不同房间，无法同队。

另外确认了角色技能数据的存储形态：`taiwan_cain_2nd.skill.skill_slot` 是
`uint32 明文长度 + zlib` 压缩的槽位表（charac_no=22 解出 408 字节，槽位为小端 uint16，
含 260/303/425/374… 等已学技能索引），但目录要求的 235 不在其中。要造出“可施法”的机器人，
要么让机器人学会目录技能（改存档），要么在目录里补一条该角色已学技能的条目（需要正确的
state 数据），两者都需要额外验证，本轮未做。

结论：**攻击/击杀仍无实机证据**，且原因已定位到职业与技能两条硬前提，而不是链路问题。

## 让机器人学会目录技能（2026-11-21，存档侧尝试）

既然攻击的硬前提之一是“目录技能已学”，就在隔离实例里直接改存档做了实验：

- `taiwan_cain_2nd.skill.skill_slot` 的格式已确认：`uint32 明文长度 + zlib`，明文是小端
  uint16 技能索引数组（charac_no=22 共 408 字节，含 260/303/425/374…）；
- 先把整行备份到 `taiwan_cain_2nd.bak_skill_22`，再把第一个空槽改成 `eb 00`（235，即目录里
  职业 9 的唯一技能），重新压缩写回；
- 改后角色仍能正常登录（`online True`），说明没有破坏存档结构。

但要确认它是否真的让 `learned_candidates` 变成 1，还需要一次成功的副本会话——本轮最后几次
尝试里机器人没有进入房间（队长侧 `party=true`，但机器人侧没有 `PARTY_AUTO_ACCEPT`），
因此**该改动尚未取得效果证据**。备份表保留，可随时回滚。

下一步：用上一轮已复现的固定顺序（机器人重登 → 队长边等实体边推动 → 邀请 → 进图）再跑一次，
观察 `[PARTY_DUNGEON_SKILL_PROFILE] learned_candidates` 与是否出现 `[PARTY_DUNGEON_SKILL]`。

## 邀请改成轮询（2026-11-21）

原先的邀请是一次性扫描：等固定时长后取实体表快照，逐个发请求。机器人在别处走动时经常扫不到，
导致“有时能组队、有时不能”。改为**轮询**：30 秒窗口内每 600ms 扫描一次实体表，对每个新出现的
非自身实体立即发出组队请求，收到队伍快照或超时再退出。实机在 02:53 一次成功
（`invited 7 at (966,306)` → 机器人 `[PARTY_AUTO_ACCEPT] peer_unique_id=8`），
同一窗口内连续两次运行也都能进图并产生 `[PARTY_DUNGEON_MOVE]`。

另把 `run_probe.ps1` 的日志尾部从 45 行放宽到 70 行：之前 `Select-Object -Last 45` 会把登录、
实体表、邀请这些前段日志裁掉，排查时看不到关键信息。

技能存档补丁已确认落在库里（解压后索引表含 235，`has235 True`），但**仍未观察到
`learned_candidates>0` 的新档案行**——实例重启后的两次运行机器人没有进房（机器人侧无
`PARTY_AUTO_ACCEPT`），因此施法效果依旧未验证。

## 按会话 id 直接邀请（2026-11-21）

实体表轮询仍然会漏：机器人走动时实体 id 与时刻都在变，靠“看到再邀请”存在概率性失败。改为
从服务端登录日志取**会话 id**（`[USER LOGIN] ... (SlotIDX: N)(IncreID: M)`，其中 M 就是
该连接的唯一 id），再用 `DNF_LIVE_PEER` 直接对该 id 连续邀请。实测一次成功：

```
[PARTY_AUTO_ACCEPT] uid=17000020 peer_unique_id=3 request_id=0     ← 03:00:42
[PARTY_DUNGEON_MOVE] uid=17000020 peer=17000015 from=(970,300) to=(1010,300)
[PARTY_DUNGEON_MOVE] uid=17000020 peer=17000015 from=(1450,300) to=(1490,300)
```

至此“邀请 → 进图 → 看到怪 → 移动”都可以在一次运行里稳定复现，不再依赖偶然的实体广播。

技能侧仍无进展：存档补丁确实在库里（`has235 True`），但重启后的运行没有产生新的
`[PARTY_DUNGEON_SKILL_PROFILE]` 行，也没有 `[PARTY_DUNGEON_SKILL]` 施法记录，
因此**施法与击杀仍未被证实**。下一步应确认技能档案在重启后是否真的重建
（可在 `ensurePartySkillProfileUnsafe` 的早退分支加一条原因日志）。

## 学会技能包解析被一个零级条目整包废掉（2026-11-21）

定位“重启后再也不出现 `SKILL_PROFILE`”的原因：不是档案没重建，而是**技能包解析失败**。
加诊断后拿到原始 240 字节（`reason=learned-parse`），按槽位表解出来是：

```
slot0 id4 lvl1 | slot1 id47 lvl1 data3 | ... | slot9 id235 lvl0 | ... 共 26 条
```

第 10 条正是我上一轮塞进存档的 235（**等级 0**）。旧解析器遇到 `level == 0` 直接整包返回失败，
于是 `partySkillInfoKnown` 永远为 false，技能档案不再加载——一次“半成功”的存档改动，
把整个施法链路静默关掉了。

修复（产品代码）：结构合法但 `level == 0` 或 `id == 0` 的条目改为**跳过**，只有真正的结构
错误（截断、重复槽位）才判整包失败。新增 3 条单测覆盖跳过/截断/重复槽位。

实机复核：修复后 `[PARTY_DUNGEON_SKILL_PROFILE_INFO] reason=learned-parsed learned=25`
（该角色实际已学 25 个技能），档案恢复加载。`learned_candidates` 仍为 0，因为目录里职业 9
只有 235 这一条、而它是 0 级——这是目录与角色不匹配，不是解析问题。

另外查清 PVF 侧状态数据的覆盖面：`skill_state_catalog.json` 只含**职业 8（38 条）与职业 10
（8 条）**，职业 9 没有任何 state 数据。所以要实机验证施法，必须换一个**职业 8** 的机器人角色。

## 实机通关：零配置选技能 → 寻怪 → 接近 → 攻击（2026-11-21）

上一轮定位到“只有职业 8/10 有 PVF 状态数据，而能登录的机器人只有职业 9”。换个思路解决：
**让机器人自己创建一个职业 8 的角色**。把 `robot_config.ini` 的 `jobs` 临时限制为 `8`，
调用 `createRobots {count:1}`，机器人通过自己的建角路径造出：

```
uid=17000021 cid=23 job=8 level=55 狂虎帝 艾尔文防线(1/0)
```

这条角色能正常登录（与 17000020/cid22 一样走机器人自建路径，不是库里预置的坏档）。
夹具再把队长动作换成“带旧式技能状态”的帧（`buildPartyLegacySkillStateBody(..., 8, ...)`），
让机器人确认队长使用的是旧式通道。实机日志完整走通：

```
[PARTY_DUNGEON_SKILL_PROFILE_INFO] learned=14
[PARTY_AUTO_ACCEPT] peer_unique_id=7
[PARTY_DUNGEON_SKILL_PROFILE] job=8 auto=true whitelist=40 pvf=38 pvf_matched=38 kept_without_pvf=2 learned_candidates=4
[PARTY_DUNGEON_MOVE] from=(970,300) to=(1010,300)
[PARTY_DUNGEON_NAV]   active=true move=true reason=move
[PARTY_DUNGEON_ATTACK] job=8 state=8 step=0 target=11020103 recover_in=900ms
[PARTY_DUNGEON_ATTACK] ... step=1/2/3 ...  ← 四段连击循环
```

这一次同时证明了：

- **零配置技能自动选择在生产实例上有效**：`mode=auto`、40 条候选、38 条命中 PVF、4 条可施放；
- 机器人会**自己走进攻击距离**（`reason=move`）并**连续攻击**同一目标（`step` 0→3 循环）；
- 攻击用的是旧式通道 `state=8`（普攻），与目标职业（8）匹配。

## 跨平台交叉验证：Linux 客户端 ↔ Windows 服务端（2026-11-21）

## 队伍帧解析热路径的分配削减（2026-11-21）

给副本帧路径补了基准（`party_dungeon_observe_bench_test.go`），基线为：

```
BenchmarkObservePartyDungeonFrame   410.9 ns/op   320 B/op   3 allocs/op
BenchmarkPartyDungeonFrameBodies     30.9 ns/op    48 B/op   1 allocs/op
```

`observePartyDungeonFrameUnsafe` 原先先用 `partyDungeonFrameBodies` 造一个 `[][]byte` 再逐条处理，
那是纯垃圾。改为**原地遍历**（type 2 单体直接处理，type 1 按长度前缀逐段处理），帧长校验与
类型判断保持等价。结果：

```
BenchmarkObservePartyDungeonFrame   387.4 ns/op   272 B/op   2 allocs/op
```

即 −5.7% 时间、少一次分配、少一个中间切片，代码也更短。

另外试过把运动体与命令体的解码缓冲改成栈数组，**反而更差**（468 ns/op、720 B/op）：返回的
`entries` 让栈数组整体逃逸成一次大分配。已回滚，只保留真正有收益的原地遍历。

需要说明量级：机器人每帧只处理一次，按 40–100 帧/秒算是每秒几十微秒，绝对价值有限；
这条基准的主要意义是把这块路径的代价固定下来，后续改动可以对照。

## 技能档案的身份缓存（2026-11-21）

`queryPartySkillProfile` 每次登录都要查一次 `taiwan_cain.charac_info` 取 `(charac_no, job)`，

## Linux 启动崩溃定位到函数级（2026-11-21）

用 WSL 自带 gdb 直接跑原版 game，拿到了崩溃现场：

```
#0 0x080fd845 in ?? ()
#1 0x082a1ebe in ?? ()
#2 0x0829f863 in ?? ()
#3 __libc_start_main
```

崩点前一条指令是 `sub $0x67b88,%esp`——**该函数一次分配约 424 KB 栈帧**，紧接着就 SIGSEGV。
对照参考工程，`0x080fd8e4` 属于 `CInGameAdvertisementManager::InsertADExposeInfo`（同一邻域），
而崩溃发生在它之前几十字节的函数里；结合日志最后一行是
`Load In Game Advertisement Expose Info From DB(0) Complete`，可以判断崩在"广告/曝光信息"这条初始化链上。

已试过把 `ulimit -s` 从 8192 提到 65536 再启动，崩点不变，所以不是主线程栈上限问题；
`LD_PRELOAD=/dp2/libdp2pre.so` 期间还会打印一次 `wrong ELF class: ELFCLASS32` 提示（外层 64 位 shell
尝试预加载 32 位库），该库最终仍由 32 位加载器载入。

这是本轮唯一可交付的 Linux 结论：**崩溃不是随机的，位置稳定在广告曝光初始化**。下一步要看该函数
在 Windows 宿主下为何不崩（dnf-native 可能提供了不同的线程栈或不同的 DB 返回），据此决定是补宿主
行为还是修数据。

Windows 实例与零配置开关已恢复。

## Linux 启动崩溃的根因：堆把栈挤没了（2026-11-21）

gdb 里取到崩溃现场与内存映射，两件事对上了：

```
0x80fd83f: sub $0x67b88,%esp        ← 该函数分配约 424 KB 栈帧
=> 0x80fd845: movl $0x67b60,0x8(%esp)   ← 立刻 SIGSEGV
$_siginfo...si_addr = 0xfff95878
```

进程映射（同一时刻）：

```
0xf7ffe000 0xffecc000  0x7ece000  rw-p  [heap]    ← 132 MB
0xfffdd000 0xffffe000  0x21000    rw-p  [stack]   ← 只有 132 KB
```

即**堆（brk）一路涨到 0xffecc000，正贴着栈底**，栈只剩 132 KB；此时任何几百 KB 的栈帧都会立即溢出。
这不是"随机环境问题"，而是 brk 与栈争地址空间的必然结果；Windows 宿主（dnf-native）自己实现 brk，
不会与栈冲突，所以同一份 ELF 在那边正常。

已试无效：把 `ulimit -s` 提到 64 MB（栈映射仍是 132 KB，brk 先占位）、开启 `setarch i386 -R`
关闭 ASLR（崩点不变）。

可行的修复方向（下一轮实施其一）：
1. 写一个 `LD_PRELOAD` 的 brk 垫片，把 brk 请求改到独立 mmap 区域（等同 Windows 宿主的做法）；
2. 启动时先把栈"撑开"（触碰若干 MB）再让游戏跑，使 brk 提前失败而不是挤压栈，观察游戏是否优雅降级。

## 两个 brk 垫片都无效：游戏绕过 libc（2026-11-21）

按上一轮的方案做了两个 32 位 `LD_PRELOAD` 垫片（zig 交叉编译，均确认已加载进游戏进程）：

1. `dnf_heap_shim.so`：`mallopt(M_MMAP_THRESHOLD, 64K)`，让 malloc 的大块走 mmap；
2. `dnf_brk_shim.so`：直接接管 `sbrk`/`brk`，用独立 mmap 竞技场（768 MB）承载 brk。

结果：**两者都不改变布局**。加垫片后 gdb 里依旧是

```
0xf7ffe000 0xffecc000  0x7ed1000  [heap]     ← 132 MB
0xfffdd000 0xffffe000  0x21000    [stack]    ← 132 KB
```

崩点也不变。这说明游戏既不通过 glibc 的 `malloc` 扩展竞技场，也不通过 PLT 调 `sbrk`/`brk`
——它很可能**直接发 `int 0x80` 的 brk 系统调用**（或自行指定高位 brk 地址）。这正是 dnf-native
在 Windows 上能幸免的原因：它拦截的是系统调用层，而我们只能用 libc 层的预加载。

要真正修好 Linux 侧启动，需要在系统调用层做（seccomp/ptrace 或改 ELF 本身），成本明显高于本轮
能覆盖的范围。当前以 Windows 实例继续推进主线，Linux 侧记录为"已知启动回归 + 根因定位完成"。

## MoveMap 会被处理，但被拒（2026-11-21）

给夹具加收包跟踪后看到关键反馈：**每个 MoveMap 发出后服务端都回一个 `typ=48 size=23` 的包**
（服务端→客户端的命令包，正是 `send_to_party_cmd_error((ENUM_CMDPACKET)0x30, code)` 的形式）。

对照参考实现的 `CParty::move_map`：

```c
if (m_state != 2) { send_to_party_cmd_error((ENUM_CMDPACKET)0x30, 0x13); return false; }
...
else if (battleField.IsClearDungeon()) { send_to_party_cmd_error(0x30, 0x13); return false; }
```

也就是说换房要求**队伍处于 state 2（房间已开始）**；我们收到错误包，说明请求被正确处理但前置状态不满足
（最可能就是队伍仍处在加载/待开始状态，或该副本被判为已通关）。

同一个响应的错误码在加密体里，本轮没能稳定复现（第二次运行时服务端没回 48 包，说明还依赖当时的队伍状态），

## Linux 启动：四种缓解全部失败（2026-11-21）

针对"brk 堆挤压栈（132 MB vs 132 KB）"这一根因，本轮又试了两种运行方式：

| 尝试 | 结果 |
|---|---|
| `setarch i386 -3`（3 GB 地址空间） | SIGSEGV，崩点不变 |
| `ulimit -d 65536`（限制数据段，逼分配器改走 mmap） | 更早失败（只打出 banner） |
| （此前）`ulimit -s 65536` | 崩点不变 |
| （此前）`LD_PRELOAD` mallopt / brk 垫片 | 游戏绕过 libc，无效 |

结论：**在当前 WSL 环境下，原版 game 无法启动**。游戏自己用高位 brk 预留竞技场，而 WSL 的栈布局
恰好被它挤到只剩 132 KB。要修只能从系统调用层（seccomp/ptrace）或直接给 ELF 打补丁，两者都超出
"环境兼容"范畴。

后续如果要做 Linux 侧实机验证，建议在**真正的 Linux 主机**（而非 WSL2）上跑——那里的地址空间布局
与当年服务器一致，大概率不会触发这个冲突。这条结论也解释了为什么 dnf-native 在 Windows 上能跑：
它自己实现 brk，不受 Linux 栈布局影响。

## 零配置技能释放：实机确认（2026-11-21）

此前夹具在队长帧里会附带"旧式技能状态"（command 5），机器人因此判定队长走旧式通道、自己也用普攻
（`[PARTY_DUNGEON_ATTACK] state=8`）。把这条帧关掉（`DNF_LIVE_LEGACY=0`）后，机器人改走**目录技能**
路径，日志出现真实施法：

```
[PARTY_DUNGEON_SKILL] uid=17000021 job=8 skill=33 state=51 level=1 name=diehard    path=sqr/character/atmage/diehard/diehard.nut
[PARTY_DUNGEON_SKILL] uid=17000021 job=8 skill=26 state=43 level=1 name=watercannon path=sqr/character/atmage/watercannon/watercannon.nut
[PARTY_DUNGEON_SKILL] uid=17000021 job=8 skill=4  state=23 level=1 name=dark_change path=sqr/character/atmage/darkchange/dark_change.nut
```

配合此前记录的档案行：

```
[PARTY_DUNGEON_SKILL_PROFILE] job=8 auto=true whitelist=40 pvf=38 pvf_matched=38 learned_candidates=4
```

可以确认**"只开技能开关、零配置"在实机上是成立的**：

2. 机器人按职业从目录里自动匹配到 40 条候选、其中 38 条命中 PVF；
3. 在自己已学的 4 条里挑一条，用 PVF 的 state 与脚本路径发出施法包；
4. 同一个机器人会按风险等级轮换不同技能（33 / 26 / 4），不是死磕一条。

顺带说明两种攻击形态的触发条件：队长用旧式通道 → 机器人普攻（四段连击）；队长不用旧式通道 →
机器人用目录技能。两者都不是硬编码技能列表。

## 出站帧构造：7 次分配降到 1 次（2026-11-21）

给 `buildPartyDungeonMotion` 补了基准，发现它是出站热路径里最贵的一段：

```
改前  BenchmarkBuildPartyDungeonMotion  340.1 ns/op  336 B/op  7 allocs/op
改后  BenchmarkBuildPartyDungeonMotion  255.9 ns/op   80 B/op  1 alloc/op
```

改法：先按 `entries` 的 mode 位精确算出载荷长度，直接在帧缓冲里预留（`make([]byte, 7, 7+size)`），
逐字段 append，校验和就地计算、载荷就地 XOR——整个函数只剩一次分配。

过程中踩了一个自造 bug：重写时漏掉了载荷首字节的**记录条数**，解码端立刻拒收（单元测试捕获），
补回后全部测试通过。

实机复核：机器人仍正常攻击与接近（`[PARTY_DUNGEON_ATTACK] step=0..3`、`[PARTY_DUNGEON_NAV] in-range`），
说明新构造的帧被对端正确解析。

量级说明：每帧 255 ns，按每机器人 5 帧/秒、600 机器人算是每秒 0.75 毫秒的构造开销——绝对量很小，
但这是每帧都要走的路径，分配次数从 7 降到 1 对 GC 压力有实际意义。

## 一个会话只能问一次副本（2026-11-21）

给夹具加了 `DNF_LIVE_SCAN_DUNGEON=1`：在同一个会话里依次请求副本 1..8，看服务端对每个 id 的应答。

也就是说：**第一次选图之后，后续的选图请求都不再被处理**（队伍进入"已选/待进入"状态，`check_error`

对后续实验的约束很重要：**每个候选副本 id 必须用独立会话验证**，否则结论会被"只有第一次有效"污染。
下一步用独立会话分别请求 2..8，把"哪些 id 在当前世界图里可选"测出来；若全部是 8，则问题确实在世界图索引
（回到 areaType==4 这条线），若某个 id 应答不同，则说明 id 本身也参与判定。

## 选图应答的第二字节随"角色 + 副本"变化（2026-11-21）

| 角色 | 等级 | 请求副本 | 应答体 | 第二字节 |
|---|---|---|---|---|
| 贺龙 | Lv1 | 1 | `00087e0e7a7d0000` | **0x08** |
| 贺龙 | Lv1 | 2 | `000e849a87720000` | **0x0e** |
| 贺龙 | Lv1 | 3..8 | 同上 `000e…` | **0x0e** |

的某个分支（例如等级/前置条件），要么是应答包里另一层结构（例如 `[0]=0` 后紧跟的是结果枚举而非错误码）。

下一步：先用"等级足够 + 同职业"的组合（Lv55 角色请求 elven_guard 的 1 与 2）把角色维度的差异分离出来，

## 掉线真因：MoveMap 坐标越界会直接断线（2026-11-21）

把驱动改成"从服务端报告的位置起步"后（代码已改，但本轮这次替换没生效，见下），又一次对照发现：

| 运行 | MoveMap | 驱动 | 结果 |
|---|---|---|---|
| bisect2 | 不发 | 0 步 | 存活 |
| coord1 | 不发（NextRoom=0） | 3 步（坐标仍从 1000,300 起） | **存活**（`reason=0`） |
| bisect3 | 发（NextRoom=1） | 2 步 | **掉线**（`reason=10`），且 MoveMap 未发出 |

所以掉线的触发点是 **MoveMap 本身**，而不是移动帧。这与参考实现完全吻合：

```c
if (((int)req.m_y >= party->m_battleField.getMapHeight()) ||
    ((int)req.m_x >= party->m_battleField.getMapWidth()))
    return 0xfffffffb;      // 负值 → process 直接 return LineFunc(...) → 派发层断线
```

`m_x/m_y` 是与**房间地图宽高**比较的；洛兰的房间比教程图小，(1,0) 这类值越界 → `check_error` 返回
负值 → 派发层按"处理器返回非零"直接断线。教程副本 10000 的地图尺寸更大（或该分支未被命中），
所以我们之前一直收到"命令错误包"而不是断线。

结论：**过图必须发房间内合法坐标**（门的位置），不能瞎试。下一步要拿到洛兰房间的地图宽高与门坐标
（地图文件仍是 7+5 记录格式），再按真实门坐标发 MoveMap。

另外记一笔：本轮想做"从服务端位置起步"的替换没能匹配上（文本不匹配），驱动仍在用 1000,300 起算，
所以 coord1 的存活只能说明"不发 MoveMap 就不掉线"，不能说明坐标修正有效。

## 关键修正：MoveMap 报文格式一直是错的（2026-11-21）

把阶段日志改成写独立文件后（`DNF_LIVE_STAGE_FILE`），终于拿到可信序列：

```
after login: state=3 ...
sent select dungeon idx=1 type=0
sent dungeon finish loading
sent single move map cell=(0,0)
```

对照参考实现的 `read_45.inc`（MoveMap 的读取器）发现**我们的报文布局是错的**：

```c
get_byte(m_x); get_byte(m_y);          // 两个"字节"，不是 short
get_int(m_fieldF); get_int(m_field13);
get_byte(m_field17); get_short(m_trapBits);
get_short(m_1b[0..3]); ...             // 后面还有若干字段
```

我们却按 `short x @0`、`short y @2` 写 16 字节——**读取器连字段都取不完**，`read` 返回非零，
派发层按"处理器返回非零"直接断线。这解释了此前所有"发 MoveMap 就掉线"的现象，也让"坐标越界"
这个假设退居其次。

修正后（x/y 各 1 字节、报文 48 字节），`(0,0)` 这次**会话存活**（全日志 0 处 `reason=10`）。

下一步：用这个正确格式重新做坐标扫描（逐格独立会话），并重新审视教程图里固定错误包的来源。

## 换房坐标扫描（修正格式后，2026-11-21）

## 坐标是"小格号"，不是像素（2026-11-21）

`m_x/m_y` 在报文里各占 **1 字节**，所以上限 255。试了三组像素级坐标 `(1500,300)`、`(300,300)`、`(1000,600)`，
**全部断线**——因为 1500 截断成 220、600 截断成 88 之类，落点越界。这条反证了坐标语义：**是小格号**。

结合上一轮的扫描可以拼出房间网格：

| 格 | 结果 | 推断 |
|---|---|---|
| (2,0) | 断线 | x 越界 → **地图宽 = 2** |
| (0,0) | 应答 0x12 | 当前房间自己 |
| (1,0) | 无应答 | **相邻可走**（被接受但没触发加载） |

也就是说：0x12 ≈ "就是当前房间"、0x15 ≈ "不相邻"，而 `(1,0)`/`(0,1)` 才是真正相邻的两格——请求被接受，

## 过图成功：队伍真的换房间了（2026-11-21）

2. 小格号必须是相邻格（`(1,0)`/`(0,1)`），越界（x ≥ 宽）会断线；

## 带跟随者的换房：需要等 8 秒（2026-11-21）

上一轮带机器人换房时被拒（末尾是 `typ=48` 命令错误，没有 `typ=29`）。原因是**队伍里多了一个成员**：
房间要等**两个成员都完成加载**才算开始，而夹具在 FinishLoad 后只等了 4 秒就发 MoveMap，此时队伍状态
还没到"房间进行中"。

把等待改成 8 秒后重跑，收到 `… 40, 30, **29**, 30, 30, 12`——**带跟随者的换房也成功了**。
同一时段机器人日志持续输出：

```

[PARTY_DUNGEON_ATTACK] uid=17000021 job=8 step=0..3
```

说明换房期间机器人的副本循环没有中断（仍在导航与攻击）。

需要说明的验证局限：夹具在换房后**仍然发送同一个怪物与同一套坐标**（因为 `liveLeadFrames` 的内容是固定的），
所以"机器人真的到了新房间并在新房间里找怪"还不能算被证明。下一步要让夹具在换房后发送**新房间的内容**
（换一组坐标、去掉或替换怪物），再看机器人是否进入"无怪→跟随"的状态。

## 换房后的"空房间"实验（2026-11-21）

新增 `DNF_LIVE_POST_MOVE=1`：换房成功后，夹具改报**新位置（1600,500）且房间里没有怪**（配合
`DNF_LIVE_KILL_AFTER=1` 让旧怪在第一步就被宣告死亡），用来观察机器人是否"停手 + 跟随"。

实测结果：

- 夹具确实发了两批各 40 帧（驱动批 + 换房后批）；
- 机器人**停手了**：06:28:30 之后不再出现 `DUNGEON_ATTACK`，转而出现一次
  `[PARTY_DUNGEON_SKILL] skill=1 windstrike`（目录技能路径）；
- 但**没有**出现朝新位置移动的 `DUNGEON_NAV`，最后几条 nav 仍指向旧坐标。

这一条其实与设计一致：机器人的导航门禁是**"视野里有活怪"**才激活（房间进入的重放设计），
空房间里它不会自己跑，而是等队长先接敌。也就是说"空房间不跟随"是预期行为，不是缺陷。

要验证"到了新房间继续作战"，正确做法是换房后**在新位置放一只新怪**（换个 entity id），
看机器人是否在新坐标处接敌、接近并攻击；这才是闭环最后一段的正经验收。

## 换房后机器人跟到了新坐标（2026-11-21）

换房后把队长报的新位置改成 `(1600,500)` 一带，并给一只"新怪"（`DNF_LIVE_MONSTER_REF=18`）。
机器人日志给出了**过图后跟随的直接证据**：

```

[06:29:49] [PARTY_DUNGEON_NAV] from=(1850,500) to=(1900,500) active=false move=false reason=idle-no-enemy
[06:29:54] [PARTY_DUNGEON_NAV] from=(2350,500) to=(2400,500) active=false reason=idle-no-enemy
[06:29:59] [PARTY_DUNGEON_NAV] from=(1450,300) to=(1500,300) active=false reason=idle-no-enemy
```

两点结论：

1. **`y=500` 说明机器人已经用新房间的坐标在算位置**——它跟上了队长的换房（配合 `PARTY_DUNGEON_FOLLOW`
   走的是可靠通道），这就是"跟随过图"的实机证据；
2. `reason=idle-no-enemy` 说明**它不把 `0x12…` 当成有效怪**（我们注入的 id 是编造的），所以进入
   "无怪待命"状态而不是乱跑——这恰好验证了第 65 轮"导航需要活怪"的结论。

下一步：换房后在**新坐标放一只真实存在的怪物 id**（从房间数据里取，或沿用原来那只但换位置），
验证机器人会在新房间里接敌、接近、攻击——闭环最后一段。

## 新房间里接敌（2026-11-21）

换房后在新坐标放**原来那只真实怪物**（不是编造 id），机器人立即继续作战：

```
[06:31:45..49] [PARTY_DUNGEON_ATTACK] target=11020103 step=0..3
[06:31:50]     [PARTY_DUNGEON_NAV] from=(1850,300) to=(1800,300) active=true reason=in-range
[06:31:50]     [PARTY_DUNGEON_SKILL] skill=26 watercannon
```

结合第 66 轮（空房间时 `from=(1850,500)`、`reason=idle-no-enemy`）可以拼出完整行为：

| 换房后房间内容 | 机器人行为 |
|---|---|
| 有活怪（真实 id） | 继续接敌、接近、普攻 + 目录技能（不断链） |
| 无怪 / 编造 id | `idle-no-enemy` 待命，不自己乱跑，但位置仍按新房间坐标更新（y=500） |

`from=(1850,300)` 这类旧坐标是导航日志的节流显示（5 秒一条、只报变化），并不代表它还在旧房间——
空房间那次已经把"按新坐标计算"直接打了出来。

至此目标①的闭环在实机上都有对应证据：城镇跟随 → 进副本 → 寻怪 → 接近 → 零配置施法/连击 →
击杀 → 清图待命 → 换房（含跟随者）→ 跟到新坐标 → 新房间继续接敌。

## 副本结束与回城（2026-11-21）

两段观察：

1. **队长离开后**：`[PARTY_TRANSPORT_CLEARED] uid=17000021 reason=empty snapshot`，`PARTY_DUNGEON_*`
   立即停止——机器人退出副本循环、清掉队伍通道，不会在无队长时继续空转；
2. **随后的城镇会话**：机器人重新接队并恢复城镇跟随通道——
   `PARTY_AUTO_ACCEPT` → `PARTY_RELAY_CONNECTED` → `PARTY_IPINFO` → `PARTY_ROBOT_TQOS_READY`。

也就是说"副本 → 结束 → 回到城镇跟随"这条**状态机路径**是通的：副本态在队长消失时被清空，之后能重新
进入城镇跟随。

需要诚实标注的限制：**服务端驱动的"副本通关 → 自动回城"事件本身没有验证**，因为那需要真的把副本打通
（服务端判定所有房间清空），而我们的夹具只能模拟队长动作、无法完成服务端侧的通关判定。这一段的验收
需要真实客户端打完一张图，或用 GM 直接改副本状态。

## 放弃副本（type 42）会断线（2026-11-21）

想用"放弃副本"来验证"回城"，查到对应处理器是 `DisPatcher_GiveUpGame`（type **42**），其

## 重要更正：普通副本其实没真正进过（2026-11-21）

## Linux 启动：栈保护带方案也失败（2026-11-21）

思路是"在栈下方预留一段 PROT_NONE 保护带，让游戏的高位 brk 提前失败，而不是把栈挤到 132 KB"。
写了 `dnf_stack_guard.so`（构造函数里 `mmap(MAP_FIXED_NOREPLACE)` 预留 0xff000000 起 15 MB），
编译通过、随 `LD_PRELOAD` 注入，结果：

```
[guard] map failed at 0xff000000
… Init CipherKeyString …
Recv SIGSEGV signal
```

保护带**根本没建成**：目标地址落在游戏已建好的 heap VMA 里（heap 从 0xf7ffe000 一直映射到 0xffecc000），
`MAP_FIXED_NOREPLACE` 正确地拒绝了覆盖。而低于 heap 基址的保护带对"向上增长"的 brk 没有任何阻挡作用。

结论：**在用户态（LD_PRELOAD）已经没有可用的手段**——heap 的 VMA 一旦由游戏自己建立到栈下方，外部就无法
收回。要修只能：① 系统调用层（ptrace/seccomp）拦 brk；② 改 ELF；③ 换真实 Linux 主机。这一条按环境限制
收尾，不再继续投入。

## Linux 启动：seccomp 拦截 brk 有实质进展（2026-11-21）

此前所有用户态钩子都无效，是因为游戏**直接发系统调用**。改成用 seccomp 过滤器在**系统调用层**拦截
brk（`SECCOMP_RET_TRAP` + SIGSYS 处理器，用私有 mmap 竞技场模拟 brk），实测：

```
[brk-shim] trapping brk over an mmap arena
[brk-shim] trap nr=45 eip=f7fd6549
[brk-shim] trap nr=45 eip=f7f5e549   （连续 7 次）
```

**拦截确实生效**（此前从未捕获到 brk）。

过程中修掉一个关键错误：i386 的 syscall 走 vdso 的 `__kernel_vsyscall`（sysenter 路径），保存的 EIP
**已经指向调用点之后**，最初按 int 0x80 的惯例 `EIP += 2` 导致跳进垃圾、立刻 SIGSEGV；去掉该调整后
不再崩溃，trap 连续触发。

当前遗留问题：崩点从"Init CipherKeyString 之后"前移到"Init Taiwan Garena Auth Key"——说明模拟的
竞技场地址与游戏期望的 brk 地址不匹配（游戏第一次 brk 用的仍是原始堆地址，落在我们的竞技场之外，
于是拿到 ENOMEM）。下一步需要在第一次 brk 时对齐地址（例如把竞技场映射到原始堆基址），或按"增量"
方式模拟 brk。

环境已恢复（Windows 实例 + 零配置开关）。

## seccomp brk 垫片：进程不再崩溃，但卡在初始化（2026-11-21）

三次迭代后进展明显：

1. **竞技场映射到程序自己的堆地址**（`MAP_FIXED_NOREPLACE` 在 `brk(0)` 返回值处）：这样游戏拿到的地址就是
   它真正能写的地址，不需要地址翻译；
2. **信号处理器里禁止 stdio**：原本在 SIGSYS 处理器里 `fprintf`，而 printf 会 malloc → 再次触发被拦截的
   brk → 在"信号处理中"再次 SIGSYS → 默认动作 = `Bad system call` 直接杀死进程。去掉打印后不再出现该错误。

当前状态：进程**不再崩溃**，日志走到 `Init Taiwan Garena Auth Key ...` 后停住（进程仍存活，`ps` 计数 1），
但还没开始监听 10011。也就是说：**brk 冲突这一层已经被绕过，卡点换成了初始化阶段的停滞**。

下一步：查这个停滞（例如 `/proc/<pid>/wchan`、`strace -p`、或看它是否在等某个服务/超时），确认是垫片导致的
死循环还是别的初始化等待。

## Linux 启动：两个关键发现（2026-11-21）

### 1. 原生崩溃确实是"栈被挤"——用 ENOMEM 变体证明了

让 brk 直接返回 ENOMEM（`SECCOMP_RET_ERRNO`），再用 gdb 看布局：

```
[heap]  0xf7ffe000 0xf801f000  0x21000   ← 132 KB，不再增长
[stack] 0xfff78000 0xffffe000  0x86000   ← 536 KB，比之前 132 KB 大得多
#0 0x087bd6da  ...（完全不同的崩点与调用栈）
```

**堆不再挤压栈后，原来的 `0x080fd845` 崩溃消失了**——此前"brk 把栈挤到 132 KB"的判断得到证实。
新崩点是另一处（大概率是分配失败后解引用空指针），因为该变体让所有 brk 都失败。

### 2. TRAP 变体仍会偶发 `Bad system call`

TRAP 变体把 brk 拦到用户态竞技场，但游戏会 **exec 子进程**（日志里出现 3 次竞技场创建 = 3 个进程）；
`execve` 会**重置信号处理器**，而 seccomp 过滤器会**继承**——于是子进程里的 brk 被拦却没有处理器，
默认动作直接杀进程（`Bad system call`）。处理器里禁用 stdio 的那个修复已经验证有效（不再因嵌套 SIGSYS 死）。

### 下一步（清晰）

用 BPF 比较 brk 的**参数**（`seccomp_data.args[0]`）：允许低于阈值（例如 `0xf0000000`）的 brk 正常成功，
超过阈值才返回 ENOMEM。这样：
- 堆能正常增长到 ~240 MB（游戏够用）；
- 永远碰不到栈所在的 0xfffxxxxx 区域；
- 不依赖信号处理器，`exec` 后依然有效。

## Linux 启动：seccomp 方案的最终结论（2026-11-21）

尝试路径与结果汇总（全部为 `x/linux-server/heapsim/` 下的预加载垫片）：

| 方案 | 结果 |
|---|---|
| `mallopt` 大块走 mmap | 游戏绕过 libc，无效 |
| 接管 `sbrk`/`brk` | 游戏直接发系统调用，无效 |
| 栈下 `PROT_NONE` 保护带 | 目标地址已被 heap VMA 占用，`MAP_FIXED_NOREPLACE` 拒绝 |
| `SECCOMP_RET_ERRNO`（brk 一律 ENOMEM） | **证明根因**：堆停在 132 KB、栈涨到 536 KB、崩点转移到别处 |
| `SECCOMP_RET_TRAP` + 竞技场 | 拦到了 brk（每次运行多次 trap），但游戏会在启动过程中**重置信号处理器**，导致后续 brk 以默认动作杀死进程（`Bad system call`） |
| 阈值过滤（只拦近栈的 brk） | 游戏一次性预留约 132 MB，阈值要么挡住它、要么挡不住栈，两难 |
| 阻止游戏重置 SIGSYS（libc 层 + seccomp 层拦 48/67/174） | 仍出现 `Bad system call`，说明重置走的是我们还没覆盖到的路径 |

**结论**：根因（堆挤压栈）已被严格证明；用户在"拦到 brk"上也成功了；剩下的是"游戏在初始化期间会把我们的
SIGSYS 处理器复位"这件具体工程问题。下一步应采用**外部 ptrace 监管进程**（`PTRACE_EVENT_SECCOMP`），
由监管者直接改写子进程的 brk 返回值——那不受子进程信号处理影响。

这一条到此收尾，不再在用户态垫片上投入。环境已恢复 Windows。

## Linux 启动：找到关键差异——"通过加载器跑"才是堆基址高的原因（2026-11-21）

对比两种启动方式：

| 方式 | 堆基址 | 结果 |
|---|---|---|
| `ld-linux.so.2 --library-path … df_game_r` | **0xf5efe000～0xffed2000**（贴着栈） | SIGSEGV（栈被挤） |
| `./df_game_r`（直接执行，`/lib/ld-linux.so.2` 软链到自带加载器） | 待查 | 走到 frida/JS 桥，报 MySQL 用户 `dnf_frida` 认证失败 |

原因很清楚：**用加载器跑时，加载器是主程序**，它的 BSS 决定 brk 基址，而加载器被 ASLR 放在库区（高位），
于是堆一涨就顶到栈；**直接执行游戏**时，主程序是游戏本身（0x08048000），brk 基址在低地址，理论上离栈有 3.9 GB。

顺带确认：`ulimit -s` 从 8 MB 调到 160 MB 时，堆从 132 MB 长到 167 MB，**仍然贴着栈**——说明
`ulimit` 只影响 mmap 区起点，不影响 brk 能长到哪，之前"大栈限制"的思路不成立。

直接执行时进入的是 frida/JS 桥路径（日志里 `api_MySQL_exec /df_game_r.js`），需要 MySQL 用户 `dnf_frida`。
下一步：在 Linux 库中创建该用户（或改用 run.sh 里同样的桥接环境），验证直接执行是否能真正启动。
