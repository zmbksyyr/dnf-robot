## 二、① 地下城闭环

### 验收入口

一条命令跑完六段并逐段判定（`x/live/full_loop.ps1`），连续多次运行均 **ALL PASS**：

```
town_follow  enter_and_attack  clear_room  leave_dungeon  town_follow_again  zero_config_skill
```

每段判定都基于可观测证据：机器人坐标变化、攻击日志增量、报告击杀后攻击停止、队伍通道清理、目录技能施法增量。

### 关键实现

- **零配置技能**：只打开 `party_skill_catalog.json` 的 `enabled`，机器人按职业从目录自动匹配（40 候选 / 38 命中 PVF），
  在已学技能里挑选并施放（实测 `diehard`/`watercannon`/`dark_change`/`windstrike`），按风险等级轮换；
- **进副本与跟随**：队长 `SelectDungeon` → 机器人加载技能档案 → `PARTY_DUNGEON_NAV` 寻怪接近 → 普攻/技能 →
  击杀后 `idle-no-enemy` → 队长消失后 `PARTY_TRANSPORT_CLEARED` → 回城后重新跟到队长坐标；
- **协议修复**：`MoveMap` 的 `x/y` 是**单字节**（原按 short 写导致服务端读包失败并断线），修正后单格移动不再掉线。

## 附：换房（过图）专项结论（供后续接手）

这一项是本项目唯一没有在实机上跑通的能力，但每一步都已查清。按顺序：

1. **多房间副本存在**：教程副本 `10000` 下有 8 张地图 —
   `tutorial(0,1)_start`、`(1,1)/(2,1)/(3,1)/(4,1)/(3,2)_normal`、`(3,0)_boss`、`tutorial.map`。
   起始房是 `(0,1)`，我们一直站在这里。
2. **换房报文**：`MoveMap(48)`，body 首两字节是**单字节** x/y（曾误写成 short 导致服务端读包失败断线）。
   读取器共消费 43 字节，我们发 48 字节（补齐到密文块整数倍），字段与长度均已核对。
3. **应答**：成功时服务端发 `0x1d`（=29），失败时发 `0x30`（=48）+ 错误码；错误码来自
   `CBattle_Field::MoveMap` 的返回值。
4. **失败码 0x14 的含义**：`check_grid_clear()` 返回 false。判据是
   `m_dropCnt == 100 && m_field13 == 0` —— 而这两个字段的真实含义是 **HP 百分比**与**冠军标志**
   （见 `add_monsters_current_map`），所以 0x14 = "房间里还有一只满血的普通怪"。
5. **清怪路径**：服务端只认 `DisPatcher_DieMob`（type 39）→ `CParty::kill_monster` → `CBattle_Field::kill_monster`，
   后者用 `m_monsterMap.find(uid)` 查表，**查不到直接 return false**，查到才在末尾 `erase(it)`。
6. **uid 来源**：房间包 `0x1d` 的怪物条目（16 字节）里第 6 字节起是 `(short)m_instId`，
   条目第 14 字节是 `m_field13`。已实现 `internal/protocol/dnf/room_clear.go` 解析并上报。
7. **报文顺序**：`dispatch_sig_16.inc` 显示死亡上报是**读取顺序的平坦序列**（不是结构体的固定数组偏移），
   一只怪正好 64 字节。改成该布局后**不再断线**（此前每次上报都会 `reason=4`）。
8. **当前卡点**：上报被接受、但 `m_monsterMap` 里的条目没有被移除（换房仍 0x14），说明在
   `kill_monster` 的前置校验里被 `return false`（`find_monster(m_mobIndex)` 等），而该函数的日志级别为 1、
   服务端默认不输出，配置里也没有可调项。

**若要继续**：反汇编 `CBattle_Field::kill_monster`（0x0830bc78）里 0x0830c… 之前的分支，
确认它对 `mobPtr->m_mobIndex` / `m_roleType` / `m_hellPartyGroupIdx` 的具体要求；或在一个可控的、
单房间小副本上用真实客户端打一次，抓上行包对照字段。
## 重要更正：教程副本实际上没有进成功（2026-11-21）

用 `DisPatcher_SetPos::check_error` 做状态探针（它只在 `user->get_state() == 3` 时才允许，否则返回 0x13 并断线）：

| 场景 | SetPos 结果 | 含义 |
|---|---|---|
| 选图 10000 之后发 SetPos | **会话存活** | 服务端状态仍是 **3（城镇）** |

也就是说：**`SelectDungeon(10000)` 并没有真正把角色送进副本**——这与它返回的错误字节 8（世界图索引不满足）一致。

由此需要更正此前的表述：

- 六段验收脚本里的 `enter_and_attack` / `clear_room` 验证的是**机器人对"选图请求"的协议反应**
  （收到房间信息包后开始寻怪、攻击日志增长、收到击杀报告后停止），**不是**"服务端真的开了一个副本"；
- 城镇跟随、零配置施法、回城跟随这几段是实机成立的；
- "进副本 → 清图 → 过图 → 通关回城"这条链路**在服务端侧从未真正跑起来**，原因是选图被世界图校验拒绝（错误 8）。

这也解释了为什么换房怎么试都是 0x14：角色根本不在副本里，`m_monsterMap` 是城镇区域的数据。

**结论**：① 的真实完成度是"城镇跟随 + 零配置战斗行为已实机验证；进副本及其之后的所有环节都未能在服务端侧成立"。要真正推进，
必须先解决"选图错误 8"——即让 `Area::m_worldMapIndex` 有效（需要在类型 4 的区域里，或补上缺失的世界图配置）。
