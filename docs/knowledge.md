# Robot 运行与联调知识

整理日期：2026-11-20；联调源码基线 `2b29662f3b281315ff35e7d1183cac55f9474601`。
本文提炼仓库外实验的最终决定；历史细节见 [Windows 记录](../doc/windows.md)，
自动攻击另见 [战斗研究](combat-research.md)。证据路径均相对于工作区 `x/`。
原始抓包、账号数据、密钥、运行目录和数据库不迁入仓库。

## 宿主适配的边界已经确定

Robot 是独立项目，Windows 编译为独立 amd64 EXE，CGO 关闭；业务、协议和调度共用。
Linux 保留原 `/proc`、信号和脚本入口。公共调度、编码和协议修复同时作用于两端，
这与“Windows 专用启停实现不改变 Linux 入口”是两件事。

| 外部控制器提供 | Robot 自己负责 |
| --- | --- |
| game 目录中正确配对的密钥 | 发现并同步密钥、生成自身业务文件 |
| `--config-dir` 和宿主 profile | 配置、PVF 导出、缓存、模板、状态和日志 |
| Windows ready／stop 事件、进程生命周期 | 正常初始化、保存、排空与失败报告 |
| 服务身份及启动参数 | 市场维护、业务调度和对应平台操作 |

`conf/host-profile.json` version 1 描述 executable、原 ELF image／SHA-256、PID 文件、
工作目录、启动参数和停止事件。PID 识别要核对实际进程路径、原 ELF 身份及映射 ELF 头，
不能只认同名进程。game、auction、point 为当前运行契约必需项。
修改内存前还要核对目标和旧字节，写后回读，暂停的线程必须恢复。

Windows 的 `/root/run`、`/root/stop` 按钮置灰，API 也明确拒绝。
不增加 shell、驱动、系统服务或外部 GUI 专用业务接口来模拟它们。
Native 只管理模块生命周期和观测；Robot 启用时，其 GUI 拍卖维护入口禁用，避免两个执行者竞争。

历史 Linux ELF 尝试的 Go 386 首个致命缺口是 sigaltstack，amd64 遇到内嵌数据／线性反汇编边界。
这不是 Windows 原生 Robot 的运行依赖。只有出现新的独立目标才重开该路线，不能再次以“编译成 ELF”
当作免适配的捷径。研究来源为 `dnf-native-output/P53-performance-robot-research/`。

## 启停、重开与内存的可复用结论

### 正常退出必须等待服务端，不只等待本地 socket

最初只限制本地关闭并发，600 人退出仍积压，失效广播和错误日志进一步放大负载。
当前所有 actor 的正常退出共用 16 个并发名额，覆盖缩容、停止自动行为和进程关闭：

1. 立即停止新自动动作；合格的运行中、未组队角色先用原 CMD 7 保存并返回选角。
2. 获得原服务确认后关闭连接，再完成既有 500 ms 本地确认。
3. 每 100 ms 查询账号状态，最多等 5 秒；真正离线后才处理角色缓存并释放名额。
4. 失败／超时保留错误，不给予离线写库许可；仍遵守原存档稳定期和数据库屏障。

关闭中的等待可被取消，但取消不能视作安全离线。内部关闭预算为 25 秒，末尾保留既有清理；
600 人仅确认等待就约 19 秒，旧 15 秒不足。
历史另试“普通下线先回选角再断开”的候选仍有 35.92 秒积压与超时，已经撤回；
不能把它与最终受控的保存／退出协议混为同一通过方案。

Windows／Linux 一轮混合负载中正常停 Robot 为 23.56／22.89 秒，最大时钟积压约 1.01／1.05 秒。
Windows 在期限末尾清理最后一个连接，不能称该轮全部连接都优雅退出。
账号登录标记、实际角色、连接数应分别核对；曾出现服务端已无角色但 SQL 保留在线标记的情况。

证据：`dnf-gm-output/evidence/graceful-save-final-summary.json`、
`server-logout-*`；行为细节见 [退出记录](../doc/windows.md#批量退出的服务端确认2026-11-19)。

### Web 重开不是只把主进程拉起来

Windows 在同一主 PID 内重建运行资源，保留外部事件和进程归属；Linux 沿用原重启入口。
HTTP 必须等待 `Server.Shutdown` 排空活动响应，仅等 `ListenAndServe` 返回会使重启请求被复位。
实际回归移除该等待会失败，恢复后连续十次通过。
停止时先取消后台工作，再等已开始操作结束，不能用“主 PID 没变”证明重启请求完整结束。

Web、netstat、tasklist 等 Windows 后台子进程使用分离控制台方式，仍保留标准句柄和停止事件；
不靠隐藏错误输出来消除黑窗。Linux 继续原 `exec.Command`。

证据：`dnf-native-output/robot-http-regression.json`、`robot-http-race.log`；
`dnf-gm-output/evidence/stall-cache-windows-console.json`。

### 资源数字要使用同一口径

socket 复用 32 KiB 读缓冲；断开释放库存、摊位、组队和城镇缓存，保留重连必需的令牌与密钥。
Windows 工作集、Linux RSS、Go 堆、私有提交是不同指标。
Robot CPU 以单核为 100%；Native 标题栏按整机算力折算且包含 GUI／MySQL，不能直接比较。

历史同机 600 目标混合负载的全树驻留均值为 Linux RSS 240.2 MiB、Windows 工作集 291.3 MiB。
Windows 干净进程曾连续 900 秒保持 555–599 运行，Robot 225–334 MiB；仍有摆摊失败，
也不能据此保证长期热重启都相同。最后 Native 权限缓存修复后的另一轮 120 秒负载为 596–600 在线、
Robot 全树约 270 MiB、game 最大积压 0.574 秒。两个轮次不能合并成一个新实测。
严重退出积压的一个根因在 Native 内存权限缓存，不能一律归为 Go 内存或 Robot 调度。

证据：`dnf-native-output/linux-comparison/comparison-summary.json`、`load-550/`；
`dnf-gm-output/evidence/store-trade/cache-range-final-load-summary.json`。

## 摆摊：按规则、位置与会话分别判断

| 条件 | 已核实语义／当前处理 |
| --- | --- |
| 普通摊／分解摊碰撞 | 原 game 两类矩形均为 160×100，接触边界也算碰撞；原横向步长 120 会重叠，现在横向占位包含 160 |
| 同区域换点 | 复用会话也要发送移动，不能只改准备坐标 |
| 区域禁止交易 | 读取 PVF `[use private store]`；普通摊选点／探测排除，但不影响普通移动 |
| 村庄 7 | 原 game 有明确限制；公共自动选点策略排除普通摊／分解摊对应禁区 |
| `0x3e` 拒绝 | 结合区域和当次会话判断；不能因一次失败把根特等整个区域永久拉黑 |
| `0x3f` 无权限／`0x72` 交易处罚 | 会话拒绝，不触发换点，不污染持久化选点，不占住其他账号可用位置 |
| 登录和分解机器确认 | 完整登录后才开始单独的 20 秒确认窗口 |
| 重试仍瞬间返回旧拒绝 | 开始新尝试时失效调度层 2 秒缓存；不能靠延长等待或伪报成功解决 |

普通摊、分解摊准备和到期清理共用既有并发名额。到期清理名额不足时保留现有摊位，
下一轮重试；恢复必须等角色实际进城。否则准备与清理叠加，会出现大量连接中 actor。

手动批量操作使用 `scheduler.store_concurrent` 并行，结果保持请求顺序。
手动分配仅预留角色所有权，具体命令负责登录，避免等候中的所有角色先上线又退出重登。
同一组八人两端约 7.1 秒返回六个展示成功、两个预期拒绝；600 人受限点测试是全部明确拒绝，
不能称为 600 个成功摊位。

展示成功后还做过真实协议买家购买：买 3、拒绝超量、买余下 997、拒绝售罄，
两端物品数量、买家金币、卖家 4% 手续费及重登保存一致。协议买家不等于图形客户端点击购买。

证据均在 `dnf-gm-output/evidence/`：`stall-position-source-study.json`、
`stall-cache-final-summary.json`、`store-permission-final-summary.json`、
`store-batch-final-summary.json`、`store-session-final-summary.json`、`store-trade/summary.json`。
原始参考仅用于理解，再以固定 ELF 独立核对，不搬运参考代码／字节表。

## 市场维护、内存补丁和 PVF 的边界

- iteminfo 与订单会在原市场启动时进入内存。更换 PVF 前检查存量引用、均价和定义身份，
  备份后再同步／恢复；不能把“重新导出文件成功”当作下次启动必然正常。
- Windows `refine-banks-31` 保留均价上限 7，搜索上限 31、等级上限 127。
  不能将 GUI 的另一套锻造／均价方案直接当作 Robot 内存模型；修改必须完整核对布局和旧值。
- 已有六项市场内存补丁实际回读，组队／邮箱补丁也有目标校验与线程恢复。
  补丁写入成功、原函数通过和真实客户端功能是不同验证层级，不能从一个按钮推断全部功能。
- 搜索保护 v7 使用已有孔记录覆盖包数据，避开对 PVF 缺失物品的危险解引用；
  无记录保留原包，未知自定义 hook 拒绝覆盖。Windows 更新已识别段前备份，Linux 保留显式安装入口。
- `/root/run`、`/root/stop` 的不支持是明确的平台能力边界；其他能力应按各自业务结果报告。

详细依据见 [平台行为](../doc/windows.md#平台行为) 和相邻 Native 的 `docs/knowledge.md`。

## 文本、加密和多角色：已经排除的误判

| 问题 | 结论 |
| --- | --- |
| 城镇变成 `name_18130` | type 9 字典编号与 type 10 名称键需经 `n_string.lst` 解析，编号 0 合法；缺失引用保留 ErrorString |
| 短文本码页猜错 | stringtable 跨完整文本条目采样，整表统一选择 UTF-8／GBK／Big5，每次使用独立 Decoder；不要逐名称猜测 |
| 简繁名称不同 | 原资源语言不同；stock“復活幣”和另一 PVF“复活币”均可正确 |
| 控制台打印替换字符 | v33 核对原文件与 API JSON 均为正确“赫顿玛尔”，是外部显示编码问题，不修改产品解码器 |
| 非零密钥通知解错 | 公共 XTEA 曾有 sum 顺序及 Go `+`／`^` 括号错误，属于共用算法错误，已修复 |
| GM 改名后 Robot 仍显示旧名 | 外部改名后重新取得实际角色名称，不把长期缓存当数据库真值 |
| 指定克隆角色却进入旧角色 | 旧代码固定选第零槽；上线时从所属账号实际列表解析目标槽位 |

原 XTEA 固定答案：零密钥／零块为 `dee9d4d8f7131ed9`；密钥字节 00..0f、明文 ABCDEFGH
为 `497df3d072612cb5`。应保留两端原接口对照，不再依靠“能登录”证明所有通知解密正确。

原角色列表为 36×148 字节，职业／成长／16 位等级在 +24／+25／+26；旧 296 字节假设错误。
保留完整记录未知字段，损坏、重复、缺失或中间空槽明确拒绝；异常角色仍可查询／下线。
这些结论针对固定原 game，不能无哈希核对用于其他版本。

证据：`dnf-gm-output/evidence/encoding/`、`online-skills/`、`gm-rename/`、`gm-clone/`、
`party-combat/combat-v33/town-encoding-review.private.json`；
源码入口为 `internal/protocol/dnf/`、`internal/capability/catalog/` 与 `internal/actor/`。

## 登录拒绝与空排空：修复保存在哪个分支

2026-11-20 曾在隔离副本遇到原 ELF 断开码 36：先是错误封装标记，再是当前 PVF 不存在的旧物品，
少量涉及宠物栏。导出目录缺少某 ID 不足以证明原服务找不到物品，必须核对原资源与实际验证。
临时清理仅作用于已备份夹具，不是产品自动清背包功能。

| 提交 | 结论 | 当前保存位置 |
| --- | --- | --- |
| `1adca2f` | 跳过空的自动 actor 排空，减少无效调度 | `experiment/party-combat` |
| `0e08c63` | 保留断开码 36，暂停自动重试，显式重试建立新登录；清除旧拒绝缓存 | `experiment/party-combat` |

## 分支、验证与继续工作的规则

联调分支回到 `2b29662` 后，后续 21 个提交完整保留在 `experiment/party-combat`，末端 `2186d68`；
main 和 latest 标签仍在 `1a4c418`。旧报告所说“已推到 feature/windows-host-adapter”是当时状态，
不能直接用作现在的分支判断。
本地 bundle 与恢复收据在 `dnf-native-output/robot-history-backup-20261120-203022/` 和
`robot-combat-branch-20261120-203426/`，不需要为保留研究重新改写历史。

新修改先判断属于平台适配、公共业务修复还是实验战斗，再运行相应测试。
`go test ./...`、双平台构建证明代码／测试层面；真实登录、通知、保存、重登和图形客户端结果分别记录。
同机 Linux 比较应逐端运行并核对实际进程／数据库，避免历史 WSL 回环转发把连接送到另一套栈。
无版本变化或新反例时，复用本文列出的结论与回归入口；不要重做编码、人偶依赖或已排除的宿主路线。
